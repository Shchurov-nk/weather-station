## 0. Исходная проблема: почему всё это вообще понадобилось

Станция работала. Потом ноутбук-сервер пропал — и выяснилось, что вместе с
ним пропали: схема БД (она жила только внутри Postgres), конфиг gunicorn,
настройка systemd, набор Arduino-библиотек. Код в git был, но **код — это
меньшая часть системы**. Всё остальное было настроено руками и нигде не
записано.

Отсюда главный принцип всей перестройки:

> **Всё, что нужно для запуска системы, живёт в git.** Секреты — единственное
> исключение, и для них в git лежит шаблон (`.env.example`).

Проверка принципа — «тест чистого клона»: на машине, где есть только git и
Docker, `git clone` + заполнить `.env` + одна команда — и система работает.
Этот тест реально прогнан, см. главу 12.

## 1. Фаза 0 — фундамент (`bc5316a`)

### 1.1 Схема БД теперь в репозитории

Файл [db/migrations/001_initial_schema.sql](../db/migrations/001_initial_schema.sql):

```sql
CREATE TABLE sensor_readings (
    id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    reading_time timestamptz NOT NULL DEFAULT now(),
    temperature  real NOT NULL CHECK (temperature BETWEEN -40 AND 85),
    humidity     real NOT NULL CHECK (humidity BETWEEN 0 AND 100),
    pressure     real NOT NULL CHECK (pressure BETWEEN 300 AND 1100)
);
CREATE INDEX sensor_readings_time_idx ON sensor_readings (reading_time DESC);
```

Разбор каждого решения:

- **`timestamptz`, а не `timestamp`.** `timestamp` хранит «настенные часы»
  без указания пояса — при переезде сервера или смене TZ данные начинают
  врать. `timestamptz` хранит абсолютный момент времени (внутри — UTC);
  в локальный пояс его переводят при *отображении*. Исторические данные всё
  равно утрачены, так что это был единственный бесплатный момент сменить тип.
- **Границы CHECK — из даташита BME280 (−40…85 °C, 300…1100 гПа), а не из
  климата.** Задача ограничений — ловить *мусор* (ноль при сбое шины I2C,
  давление в сырых паскалях ~101325 вместо гектопаскалей), а не спорить с
  погодой. Диапазон «для уровня моря» 870–1085 гПа отбраковал бы честные
  ~900 гПа на высокогорье.
- **`GENERATED ALWAYS AS IDENTITY`** — современная замена `serial`:
  суррогатный ключ, который нельзя случайно вставить руками.
- **Один индекс по `reading_time DESC`** — потому что *все* запросы проекта
  ходят по времени (`ORDER BY reading_time DESC LIMIT`, диапазоны будущего
  дашборда). Индексы не бесплатны (замедляют вставку), поэтому только один
  и именно этот.

### 1.2 Мелкие честности

- В прошивке не хватало `#include "config.h"` — скетч в принципе не
  компилировался (переменные `ssid`, `serverURL` объявлены именно там).
- Удалены `#define BME_SCK 13` и т.п. — датчик подключён по I2C, эти
  SPI-пины нигде не использовались и только вводили в заблуждение.
- `.gitignore` из одной строки `testing` заменён на реальный (`.env`,
  `__pycache__/`, `.venv/`, …).
- Заголовок таблицы врал («Last 5» при `LIMIT 15`).

**Урок:** санитарный коммит перед большой работой — отдельно. Он маленький,
его легко проверить, и дальше вы строите на честном фундаменте.

## 2. Docker за 10 минут — ровно то, что нужно для этого проекта

Термины, без которых дальше никак:

- **Образ (image)** — замороженная файловая система + метаданные: «Python
  3.13, наши зависимости, наш код, команда запуска». Аналогия из DS: образ —
  это как `conda env export`, только честный — в него входит вообще всё,
  вплоть до операционной системы.
- **Контейнер** — *запущенный процесс*, которому ядро Linux показывает
  файловую систему образа и изолирует его от остальной машины. Контейнер —
  дешёвый и одноразовый: умер — создали новый из того же образа за секунду.
- **Слои и кэш.** Каждая строка Dockerfile создаёт слой. Если строка и её
  входные файлы не менялись, Docker берёт слой из кэша. Отсюда главный
  фокус всех Dockerfile: **сначала зависимости, потом код** (код меняется
  часто, зависимости — редко).
- **Volume** — именованный кусок диска, живущий *вне* контейнера. Контейнеры
  одноразовые, база данных — нет; поэтому данные Postgres лежат на volume
  `pgdata`, и пересоздание контейнера их не трогает.
- **Сеть Compose.** Все сервисы одного `compose.yaml` попадают в общую
  виртуальную сеть, где **имя сервиса = DNS-имя**. Строка
  `postgresql://...@db:5432/...` работает, потому что `db` — это имя сервиса
  в compose. Наружу (на порты машины) выставляется только то, что явно
  попросили через `ports:`.
- **Compose** — декларативное описание стека: «есть три сервиса, такие-то
  образы, такие-то volume и порты». Одна команда `docker compose up -d`
  приводит реальность в соответствие с файлом.

Мысленная модель: **Dockerfile — рецепт образа, образ — замороженный
результат, контейнер — разогретая порция, volume — холодильник, compose —
меню на весь обед.**

## 3. Зависимости: uv и lock-файл (`24bedbe`, `bb2c30f`)

Сначала `git mv app api` отдельным коммитом — git отслеживает переименование,
история файлов не рвётся, а имя каталога совпадает с сервисом в compose.

Дальше [api/pyproject.toml](../api/pyproject.toml):

```toml
dependencies = ["flask>=3", "gunicorn>=23", ...]

[dependency-groups]
dev = ["pytest>=8", "ruff>=0.8"]
```

и команда `uv lock` → файл `uv.lock` (закоммичен!).

**Почему это лучше `pip install` + `requirements.txt`:**

- `pyproject.toml` перечисляет только *прямые* зависимости с мягкими
  границами — то, что вы осознанно выбрали.
- `uv.lock` фиксирует **всё дерево** (прямые + транзитивные) с точными
  версиями и хэшами. `uv sync --frozen` ставит байт-в-байт одно и то же
  окружение сегодня, через год, в Docker и в CI.
- `pip freeze` смешивает прямое с транзитивным и не проверяет хэши; «у меня
  локально работало» происходит ровно из этой щели.

Аналогия: `pyproject.toml` — список блюд, `uv.lock` — чек с точными
граммовками. Спор о вкусах ведут по меню, воспроизводят ужин — по чеку.

Разделение `dependencies` / `dev` важно для Docker: в образ ставится только
первое (`--no-dev`) — pytest и ruff серверу не нужны.

## 4. Конфигурация через переменные окружения (`09ba151`)

Было: `from config import db_config`, где `config.py` в gitignore.
**Это и есть механизм катастрофы с ноутбуком**: файл с настройками жил только
на одной машине и умер вместе с ней, а в репозитории не осталось даже списка
того, *какие* настройки нужны.

Стало:

- код читает `os.environ["DATABASE_URL"]` (позже — pydantic-settings);
- в репозитории лежит [.env.example](../.env.example) — **полный список всех
  ручек с фиктивными значениями**;
- реальный `.env` (в gitignore) — единственное, что нужно заполнить на новой
  машине.

Почему именно env-переменные: это единственный конфиг-механизм, который
одинаково работает локально, в Docker, в compose и в CI — и он не привязан
к языку (та же `DATABASE_URL` пойдёт и в Streamlit-дашборд).

`DATABASE_URL` — стандартный формат-строка подключения:
`postgresql://ПОЛЬЗОВАТЕЛЬ:ПАРОЛЬ@ХОСТ:ПОРТ/БАЗА`.

## 5. Dockerfile построчно (`733018f`)

Файл [api/Dockerfile](../api/Dockerfile):

```dockerfile
FROM python:3.13-slim
```
База: официальный образ с Python 3.13. `-slim` — без компиляторов и лишних
пакетов (меньше размер и поверхность атаки).

```dockerfile
COPY --from=ghcr.io/astral-sh/uv:0.11 /uv /usr/local/bin/uv
```
Берём бинарник uv из его официального образа. `--from=<образ>` умеет
копировать файлы из чужих образов — так мы не ставим uv через pip.

```dockerfile
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev
```
**Сердце файла.** Копируем только два файла зависимостей и ставим их. Пока
эти два файла не меняются, слой берётся из кэша — правка `app.py` не
запускает переустановку пакетов. `--frozen` = «строго по lock-файлу, если он
рассинхронизирован с pyproject — упади». Сборка либо воспроизводима, либо
громко ломается; тихого «ну я поставил что-то похожее» не бывает.

```dockerfile
COPY . .
```
Теперь код. `.dockerignore` рядом следит, чтобы в образ не утекли `.env`,
`.venv` и тесты.

```dockerfile
RUN useradd --create-home appuser
USER appuser
```
Всё после этой строки выполняется не от root. Если в приложении найдут дыру,
атакующий окажется бесправным пользователем внутри контейнера, а не root.

```dockerfile
CMD ["gunicorn", "-w", "2", "-b", "0.0.0.0:8000", "--access-logfile", "-", "app:app"]
```
- Flask-овский `app.run()` — отладочный однопоточный сервер; в проде WSGI-
  сервер gunicorn.
- `-w 2` — два процесса-воркера. Старые 5 из README не нужны: нагрузка —
  один запрос в минуту.
- `--access-logfile -` — логи в stdout. В контейнерах не пишут логи в файлы:
  stdout собирает сам Docker (`docker compose logs api`).
- `-b 0.0.0.0` — слушать на всех интерфейсах *контейнера* (иначе Caddy из
  соседнего контейнера не достучится). Наружу машины порт всё равно не
  выставлен — его нет в `ports:` compose-файла.

## 6. compose.yaml посервисно (`733018f`)

Файл [compose.yaml](../compose.yaml). Три сервиса:

### `db` (postgres:17)

```yaml
volumes:
  - pgdata:/var/lib/postgresql/data
  - ./db/migrations:/migrations:ro
  - ./db/apply_migrations.sh:/usr/local/bin/apply_migrations:ro
  - ./db/init:/docker-entrypoint-initdb.d:ro
healthcheck:
  test: ["CMD-SHELL", "pg_isready -U $$POSTGRES_USER -d $$POSTGRES_DB"]
```

- `pgdata` — named volume: **`docker compose down` данные сохраняет,
  `down -v` — уничтожает**. Это стоит выучить до того, как наберёте `-v`.
- `:ro` — монтируем скрипты только для чтения: контейнер не может их менять.
- `/docker-entrypoint-initdb.d/` — соглашение официального образа Postgres:
  скрипты отсюда выполняются **один раз, при первом старте на пустом
  volume**. На всех последующих стартах каталог игнорируется. Отсюда же
  следствие: поменяли `POSTGRES_PASSWORD` в `.env` после первого запуска —
  в живой базе пароль **не** изменился.
- healthcheck: compose периодически спрашивает `pg_isready`; статус видно в
  `docker compose ps`. `$$` — экранирование, чтобы `$` дошёл до шелла
  контейнера, а не был подставлен compose-ом.

### `api`

```yaml
build: ./api
depends_on:
  db:
    condition: service_healthy
```

`depends_on + service_healthy` упорядочивает **только старт**: api не
запустится, пока Postgres не ответит `pg_isready`. Но если БД перезапустится
*позже*, никто api не спасёт — он обязан пережить это сам. Именно поэтому в
фазе 2 появился пул соединений (глава 8).

Обратите внимание: у `api` нет `ports:` — он доступен только внутри сети.

### `caddy`

```yaml
ports: ["80:80", "443:443"]
volumes:
  - ./caddy/Caddyfile:/etc/caddy/Caddyfile:ro
  - caddy_data:/data
```

Единственный сервис с портами наружу — **единственная дверь в систему**.
`caddy_data` хранит полученные сертификаты; без этого volume каждое
пересоздание контейнера заново ходило бы за сертификатом и упёрлось бы в
лимиты Let's Encrypt.

[Caddyfile](../caddy/Caddyfile) — пять строк:

```
{$DOMAIN} {
    handle /sensor* { reverse_proxy api:8000 }
    ...
}
```

`{$DOMAIN}` подставляется из env. Локально `DOMAIN=localhost` — Caddy сам
выпускает self-signed сертификат; на VPS `DOMAIN=имя.duckdns.org` — Caddy
сам получает и продлевает Let's Encrypt. **Один конфиг на оба мира** — ради
этого и выбран Caddy вместо nginx+certbot (там то же самое — это два
инструмента и ~40 строк).

### Least privilege в переменных

Каждому сервису — свой явный список `environment:`, а не общий `env_file`.
Будущий дашборд не увидит `SENSOR_TOKEN` и суперпароль БД: если его
скомпрометируют, утечёт только read-only доступ.

## 7. Миграции без Alembic (`733018f`)

Задача: схема должна применяться сама — и при первом запуске, и при будущих
изменениях. Решение из трёх частей:

1. **[db/apply_migrations.sh](../db/apply_migrations.sh)** — ~30 строк bash:
   таблица `schema_migrations` (какие файлы уже применены), цикл по
   `/migrations/*.sql` в алфавитном порядке, каждый новый файл — внутри
   одной транзакции вместе с записью в учётную таблицу (`psql
   --single-transaction -f файл -c INSERT...`): либо применилось и учлось,
   либо ни то ни другое. Повторный запуск ничего не делает — это и
   называется **идемпотентность**.
2. **[db/init/01_bootstrap.sh](../db/init/01_bootstrap.sh)** — крючок первого
   запуска (см. `/docker-entrypoint-initdb.d` выше): создаёт роль
   `dashboard_ro` и зовёт раннер. Роль создаётся в `.sh`, а не в миграции,
   потому что в `.sql`-файлах нет подстановки env-переменных, а пароль роли
   приходит из `.env`.
3. **Дальнейшие миграции**: кладёте `003_что_то.sql` в `db/migrations/` и
   выполняете `docker compose exec db apply_migrations` — тот же скрипт, та
   же учётная таблица.

Почему не Alembic/Flyway: у проекта одна таблица и изменения «только
вперёд». Таблица учёта — ровно та же идея, что внутри взрослых инструментов,
но здесь она вся видна и понятна. Когда миграций станет много — переезд на
Alembic тривиален.

Роль `dashboard_ro` создана **уже сейчас**, хотя дашборда ещё нет: роли и
гранты должны попасть в базу при первом init, иначе в фазе 5 пришлось бы
доделывать живую базу руками — снова недокументированное состояние.

## 8. psycopg3 и пул соединений (`f9e44f3`)

Замена `psycopg2-binary` → `psycopg[binary]` + `psycopg-pool` и файл
[api/db.py](../api/db.py):

```python
_pool = ConnectionPool(settings.database_url, min_size=1, max_size=4, open=True)
# доступ ленивый, через get_pool()
with get_pool().connection() as conn:
    conn.execute(...)
```

Три причины:

1. **У старого кода была скрытая течь.** У psycopg2 `with conn:` управляет
   *транзакцией*, но **не закрывает соединение** — старый код бросал
   соединения сборщику мусора. С пулом соединение явно возвращается в пул.
2. **Устойчивость к рестартам БД.** Соединение-на-запрос умирает вместе с
   перезапуском Postgres; пул сам переустанавливает соединения. Помните
   `depends_on` из главы 6: после старта вы сами по себе.
3. psycopg2 — в режиме поддержки; psycopg3 — живой преемник с нормальным
   API (`conn.execute(...)` без ручного курсора).

Честная оговорка: при одном запросе в минуту пул — не про производительность
вообще. Он про правильный паттерн, который не придётся переделывать, когда
появится дашборд.

`get_pool()` ленивый (создаётся при первом обращении), чтобы импорт модуля —
например, в тестах — не лез в базу.

## 9. Усиление API (`00642c6`)

[api/app.py](../api/app.py) — три рубежа до того, как данные коснутся БД:

### Рубеж 1: аутентификация (401)

```python
secrets.compare_digest(header.removeprefix("Bearer "), settings.sensor_token)
```

Bearer-токен — общий секрет между прошивкой и сервером. `compare_digest`
вместо `==`: обычное сравнение строк отваливается на первом несовпавшем
байте, и по времени ответа можно подбирать секрет посимвольно (timing
attack). Для домашней станции это перестраховка, но правильный рефлекс
стоит дёшево.

### Рубеж 2: валидация (422)

[api/schemas.py](../api/schemas.py): pydantic-модель с теми же границами,
что CHECK-и в БД. Зачем дублировать? **Разные задачи**: pydantic отдаёт
клиенту внятный ответ «hum=150 вне диапазона 0–100» (422), а CHECK — рубеж
последней надежды, если API когда-нибудь обойдут. Правило: **валидируй на
границе, ограничивай в хранилище**.

[api/config.py](../api/config.py) — pydantic-settings: обязательные
`database_url` и `sensor_token` читаются из env **при старте**. Забыли
переменную — процесс не поднялся и сказал какую. Это сильно лучше, чем
падение на первом запросе в три часа ночи.

### Рубеж 3: гигиена ошибок (500)

Было: `return jsonify({"error": str(e)}), 500` — текст исключения psycopg
уходил клиенту (имена таблиц, куски SQL — разведданные для атакующего).
Стало:

```python
except Exception:
    logger.exception("insert failed")          # стектрейс -> в логи
    return jsonify({"error": "internal server error"}), 500   # клиенту -> ничего
```

Полная информация — себе (`docker compose logs api`), клиенту — ничего.

### Тесты (`9cafcb6`)

[api/tests/test_api.py](../api/tests/test_api.py) — 7 тестов через Flask
test client. База не нужна: `get_pool` подменяется моком —

```python
with mock.patch.object(app_module, "get_pool") as gp: ...
```

Проверяется поведение *границы*: 401 без токена и с неверным токеном; 422 на
мусор (и что до БД дело не дошло — `assert_not_called`); 201 на валидное;
и отдельный тест, что текст внутренней ошибки **не просачивается** в ответ.

Запуск: `cd api && uv run pytest`.

## 10. Почему ESP32 будет ходить по HTTPS с пиннингом корня

Решение для транспорта через публичный интернет (реализация — шаг 8
runbook-а):

- TLS решает **две** задачи: шифрование *и* проверку, что сервер — ваш.
  `setInsecure()` в ESP32-коде даёт только первое: активный
  man-in-the-middle подсунет свой сертификат, примет соединение и получит
  ваш токен.
- Прошивка проверяет сертификат сервера по зашитому **корневому**
  сертификату Let's Encrypt (`setCACert`, ISRG Root X1 + X2). Серверный
  (leaf) сертификат меняется каждые ~60–90 дней — но подписан он всегда
  цепочкой от корня, а корень живёт до 2035. Прошивку не придётся трогать
  годами.
- **NTP обязателен до первого запроса**: проверка сертификата сравнивает
  срок действия с текущим временем, а ESP32 просыпается с часами в 1970
  году — рукопожатие будет «загадочно» падать.
- Отвергнутые альтернативы: WireGuard — лишняя движущаяся часть ради данных
  о погоде (а TLS для дашборда всё равно нужен); чистый HTTP+токен — токен
  летит открытым текстом, перехватил — пиши мусор в базу.

## 11. Runbook как жанр (`d86b282`)

[docs/vps-runbook.md](vps-runbook.md) — пошаговая инструкция для VPS:
пользователь `deploy` и запрет паролей → ufw → автообновления → swap (у
машины ~1 ГБ RAM) → Docker → деплой → `nmap`-проверка снаружи → патч
прошивки → бэкапы с обязательным restore-тестом.

Два принципа, которые стоит унести с собой:

- **Порядок шагов не случаен**: SSH-ключи и firewall — *до* установки
  Docker, потому что членство в группе `docker` эквивалентно root.
- **Бэкап без проверенного восстановления — гипотеза, а не бэкап.** Приёмка
  фазы — не «дамп создаётся», а «я развернул дамп в одноразовый контейнер и
  сверил count(*)». И копия дампов забирается с VPS *pull-ом* с домашней
  машины: скомпрометированный сервер не должен иметь ключей к чему-либо ещё.

## 12. Приёмка: что было прогнано и как повторить

Всё локально, из корня репозитория (Docker установлен, `.env` заполнен):

```bash
# 0. Стек с нуля
docker compose up -d --build
docker compose ps                      # db должен стать (healthy)
docker compose logs db | grep apply    # обе миграции применились сами

# 1. Поведение API (подставьте токен из .env)
curl -sk -o /dev/null -w '%{http_code}\n' -X POST https://localhost/sensor \
     -H 'Content-Type: application/json' -d '{}'                    # 401
curl -sk -o /dev/null -w '%{http_code}\n' -X POST https://localhost/sensor \
     -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"temp":21.5,"hum":150,"pres":995}'                        # 422
curl -sk -o /dev/null -w '%{http_code}\n' -X POST https://localhost/sensor \
     -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"temp":21.5,"hum":40.2,"pres":992.1}'                     # 201

# 2. Идемпотентность миграций
docker compose exec db apply_migrations          # skip, skip

# 3. Данные переживают пересоздание контейнеров
docker compose down && docker compose up -d      # count(*) не изменился

# 4. Схема пересоздаётся сама на пустом volume (УНИЧТОЖАЕТ данные!)
docker compose down -v && docker compose up -d   # чистая БД, 2 миграции

# 5. Оборона в глубину — CHECK ловит мусор даже мимо API
docker compose exec db psql -U weather -d weather \
  -c "INSERT INTO sensor_readings (temperature, humidity, pressure) VALUES (20,150,990)"
# ERROR: violates check constraint

# 6. Read-only роль действительно read-only
docker compose exec db psql -U dashboard_ro -d weather \
  -c "INSERT INTO sensor_readings (temperature, humidity, pressure) VALUES (20,50,990)"
# ERROR: permission denied
```

Все пункты прошли 2026-08-12 на этой машине. Единственная местная
особенность: на ней не работает сеть хост↔контейнер (curl с хоста не
проходит; тесты пункта 1 выполнялись из контейнера в той же docker-сети),
и поэтому сборка делалась с `docker build --network=host`. Это дефект
конкретной машины (Ubuntu 26.04 + Docker 29), не проекта — контейнеры друг
с другом общаются нормально, чего стеку достаточно.

## 13. Упражнения для закрепления

1. **Слои и кэш.** Поменяйте строку в `api/app.py` и запустите
   `docker compose build api`. Посмотрите, какие шаги взялись из кэша
   (`CACHED`) и почему установка зависимостей не повторилась. Потом добавьте
   любой пакет в `pyproject.toml` (не забудьте `uv lock`) и сравните.
2. **Миграция своими руками.** Создайте `db/migrations/003_test.sql` с
   `CREATE TABLE playground (id int);`, примените через
   `docker compose exec db apply_migrations`, убедитесь по
   `SELECT * FROM schema_migrations`, что файл учтён, и что повторный запуск
   его пропускает. Потом удалите таблицу и файл — и подумайте, почему
   раннер «не заметит» удаления (подсказка: миграции — только вперёд).
3. **Least privilege.** Попробуйте из контейнера api достучаться до БД под
   `dashboard_ro` и сделать `UPDATE`. Объясните, на каком уровне вас
   остановили.
4. **Здоровье стека.** Убейте контейнер БД (`docker kill
   weather-station-db-1`) и посмотрите: что сделает `restart:
   unless-stopped`, что покажет `docker compose ps`, переживёт ли это пул
   соединений api (отправьте измерение до и после).
5. **Проверьте себя по вопросам:** чем volume отличается от bind mount
   (`./db/migrations:...` — это который?); почему `.env` не должен попадать
   в образ и что этому мешает; почему pydantic-границы и CHECK-и дублируются
   сознательно; зачем `$$` в healthcheck.
